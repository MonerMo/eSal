Smart Receipt (eSal) — Mobile API Reference

AMAD Hackathon · Backend for the Swift mobile app · Prepared 2026-07-12

Base URL: https://<your-render-app>.onrender.com — replace with the actual Render deployment URL you've been testing against in Postman. All paths below are relative to this base URL.

General Conventions

Authentication

Every endpoint marked JWT REQUIRED needs this header on the request:

Authorization: Bearer <accessToken>

The accessToken comes from POST /auth/login. There is no separate "get current user id" call needed — the token is self-contained; the backend extracts the user's identity from it. The app never sends a user id anywhere itself.

Error response shape

All errors (validation, auth, not found, etc.) come back as JSON in Nest's standard shape:

{
  "statusCode": 404,
  "message": "Receipt not found",
  "error": "Not Found"
}

message can also be an array of strings specifically for request-validation failures (missing/invalid fields), e.g. ["email must be an email", "password must be longer than or equal to 8 characters"].

Important — Decimal fields serialize as JSON strings, not numbers.
Every money/quantity field (subtotal, tax, serviceCharge, discount, total, quantity, unitPrice, totalPrice, totalSpendingThisMonth, totalSpending, category total) is a Prisma Decimal under the hood. Decimals serialize to JSON as quoted strings (e.g. "total": "49.90"), not bare numbers — this is deliberate on Prisma's part, to avoid floating-point precision loss on money values. Swift's default JSONDecoder will fail to decode a quoted string directly into a Double/Decimal property — you'll need to either decode these fields as String and convert, or use a custom decoding strategy. The one exception: when a sum has no data to sum (e.g. no spending this month yet), the backend currently returns the plain number 0 instead of a Decimal string — so these specific fields can arrive as either a string or a number. Decode defensively.
Dates (createdAt, updatedAt, warrantyEndDate) are standard ISO-8601 UTC strings, e.g. "2026-07-11T18:21:29.123Z".
HTTP status codes on POST /auth/signup and POST /auth/login: both currently return 201 on success (NestJS's default for @Post() routes when no status override is set), not 200. Check for the 2xx range rather than hardcoding 200 for these two.

JWT REQUIRED

Powers the Insights screen — total spend plus a per-category breakdown for a selectable time range.

Query parameters
ParamValuesDefault

Note the different vocabulary from the Receipts screen: Insights uses thisMonth/lastMonth/3months, while Receipts uses thisWeek/lastMonth. Don't reuse one range enum for both screens in the app.
Example requests
GET /insights
GET /insights?range=lastMonth
GET /insights?range=3months
Success response — 200
{
  "range": "thisMonth",
  "totalSpending": "560.40",
  "categories": [
    { "category": "Electronics", "total": "228.85" },
    { "category": "Groceries", "total": "331.55" }
  ]
}

categories is sorted by total descending. A category with no spending in range is simply absent from the array (not returned as zero). If a line item somehow has no assigned category, it's grouped under "Uncategorized". Empty range → "totalSpending": 0, "categories": [].

8. Apple Wallet Pass

GET /passes/wallet

JWT REQUIRED

Returns a signed .pkpass file for the logged-in user — this is the customer's membership card / wallet-token carrier, and is how the app hands the customer's claim QR code to Apple Wallet. The raw walletToken value never needs to be exposed to the app as JSON anywhere; it's baked directly into the pass's barcode by the backend.

Response — 200
HeaderValue
Content-Typeapplication/vnd.apple.pkpass
Content-Dispositionattachment; filename="esal.pkpass"

Body is the raw binary .pkpass file (a signed zip archive). On iOS, fetch it as Data, then:

let pass = try PKPass(data: passData)
let vc = PKAddPassesViewController(pass: pass)
present(vc, animated: true)

The pass contains a PKBarcodeFormatQR barcode encoding the user's walletToken, their name, "Member Since" date, and account type. This is what the customer shows at checkout for the store's Raspberry Pi (GM65 scanner) to read and claim the receipt against their account.

Error responses
StatusMessageWhen
401"Unauthorized"Missing/invalid JWT
404"User Doesn't Have Wallet Token"User's walletToken is null (shouldn't normally happen — it's set automatically at account creation)
409"Shop Owner Not Linked To A Store"Only relevant for SHOP-type accounts, not the customer app's flow

Shop Owner Endpoints

Requires a fresh login. These 4 endpoints rely on accountType and storeId now being embedded in the JWT at login time. Any accessToken obtained before this change was deployed will not carry those claims and will be rejected with 403 by every endpoint below — call POST /auth/login again to get a token that works with them. This does not affect any of the customer endpoints above, which never read those claims.

All 4 endpoints below share the same guard stack: JWT REQUIRED and the account must be accountType: "SHOP". A CUSTOMER token calling any of these gets a 403, not empty data.

StatusMessageWhen (applies to all 4 endpoints below)
401"Unauthorized"Missing/invalid JWT
403"This endpoint is only available to shop accounts"Token belongs to a CUSTOMER account
403"Shop account is not linked to a store"Defensive case — shouldn't happen in practice, since a store is created atomically at signup for SHOP accounts
Privacy by design: none of these endpoints ever return the identity (name/email/phone) of the customer who claimed a receipt — only the receipt's status ("PENDING" = unclaimed, "ASSIGNED" = claimed by some customer). This was a deliberate choice, not an oversight.

Not Included In This Doc

The backend also has a /devices module (POST /devices/pair/qr, POST /devices/pair/nfc, GET /devices/pair/status) and two receipt endpoints (POST /receipts, POST /receipts/:id/claim/qr). These are deliberately excluded from this document because the customer mobile app never calls them:
  • POST /receipts and POST /receipts/:id/claim/qr are called by the Raspberry Pi itself, authenticated with a per-device API key (x-api-key header), not a customer JWT.
  • The /devices/pair/* endpoints are the one-time flow a shop owner uses to link a new Pi to their store — separate from viewing receipts/dashboard/insights, which is now documented above. No device-pairing screens have been shared yet, so that part stays excluded for now.
Security note (not blocking, but worth knowing): GET /devices/pair/status currently has no authentication guard at all — anyone who knows (or guesses) a device's pairingId can call it and receive that device's apiKey in plain JSON. This is the same class of issue as the earlier device.apiKey leak that was fixed on /receipts, just in a different endpoint. It's not part of today's build, flagging it here so it doesn't get forgotten.

Known Gaps / Open Items

1. Store branding fields are currently empty. taxId and logoUrl are null on the test store used for development. Set them in Prisma Studio before a demo that shows store branding on the Receipts/Details screens.
2. Smart Offers are mocked. The smartOffers array on /dashboard is hardcoded placeholder content — there is no real recommendation logic behind it.
3. Language and notification toggles are client-side only. Confirmed — no backend persistence, no endpoint to call for these Profile screen settings.
